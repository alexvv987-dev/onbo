# Design

## Context

См. proposal.md. Сейчас `cmd/onbo` и `cmd/mock` читают окружение самостоятельно, `agent.NewFromEnv` делает это повторно, а timeout и ограничения заданы в нескольких пакетах. `cmd/eval` использует GigaChat без прикладной БД. Существующие тесты передают зависимости напрямую и подменяют окружение; запуск Compose переопределяет часть настроек. Пользователь выбрал YAML плюс окружение. Изменение пересекает несколько пакетов и добавляет YAML-разбор, поэтому требуется отдельный design.

## Goals / Non-Goals

**Goals:** единое место загрузки; явные типы; настройки, передаваемые конструкторам; строгие ошибки до сети; понятная принадлежность констант; осмысленные имена без однобуквенных объявлений; сохранение поведения на корректных прежних настройках.

**Non-Goals:** горячая перезагрузка, внешнее хранилище секретов, Viper/DI-контейнер, переработка слоёв Store, новые бизнес-функции, миграции схемы, изменение frontend. Константы не превращаются в пользовательские настройки, если задают фиксированный контракт MVP.

## Decisions

### 1. Структура и загрузка

Добавить `internal/config/config.go` с типами Config, Mock, HTTP/MockHTTP, Redis, Agent и связанными настройками Store/сессий. Публичные точки загрузки разделить по процессам: App требует БД/Redis/имитацию, Mock — БД/межсервисный токен, Agent для eval — только режим и параметры модели. Пакет не зависит от backend/agent/mock и не создаёт клиентов. Прикладные конструкторы не читают окружение. `agent.NewFromEnv` при необходимости остаётся тонкой совместимой обёрткой над загрузчиком Agent.

Порядок: defaults из тегов env-default без чтения окружения → строгая проверка и декодирование одного снимка YAML через cleanenv.ParseYAML → cleanenv.ReadEnv с проверкой явно присутствующих env → проверка итогового объекта. Непустое CONFIG_FILE выбирает явный путь; иначе стандартные `configs/onbo.yaml`/`configs/mock.yaml`, относительно рабочего каталога. Для eval применяется onbo.yaml, но проверяется только конфигурация Agent. Отсутствие неявного стандартного файла допустимо, остальные ошибки чтения — нет. Пустой CONFIG_FILE эквивалентен незаданному; пустой env для обязательного поля очищает значение и приводит к ошибке. Пустой bool/duration/int недопустим; optional строка может очищаться.

По уточнению пользователя использовать github.com/ilyakaznacheev/cleanenv v1.5.0; типизированные настройки имеют yaml/env/env-default/env-required теги и обычные time.Duration. До cleanenv.ParseYAML проверять снимок через go.yaml.in/yaml/v3 v3.0.6: типы scalar, неизвестные/повторные ключи, единственный документ и размер 64 KiB. Файл повторно не открывать: cleanenv.ReadConfig заменён эквивалентной последовательностью ParseYAML + ReadEnv для сохранения строгой проверки и поддержки YAML без расширения. Длительности проверять через time.ParseDuration, без подстановки ${ENV} внутри YAML. MustLoad(path) Config / MustLoadMock(path) Mock — fail-fast обёртки; Load/LoadMockFile возвращают безопасную ошибку для тестов и управляемого запуска.

### 2. Файлы и приоритеты

`configs/onbo.yaml` содержит несекретные секции HTTP, lifecycle, Redis address/timeout/session, mock URL/timeout, LLM mode/model/endpoints/scope/CA и эксплуатационные ограничения. `configs/mock.yaml` содержит HTTP, lifecycle, health timeout и лимит входного тела имитации. У каждого файла только поля своей схемы. Конфигурации поставляются в репозитории и runtime-образе; Compose явно выбирает файл каждого сервиса через CONFIG_FILE.

Полный `DATABASE_URL`, `REDIS_PASSWORD`, `MOCK_TOKEN`, `GIGACHAT_AUTHORIZATION_KEY` существуют только как env-поля runtime-структур и отсутствуют в разрешённой YAML-схеме. Значения секретов не сериализуются и не включаются в ошибки; сообщения декодера/парсера оборачиваются безопасно, без исходных строк YAML или env. Ключи/имена полей допустимы в диагностике.

Сохранить текущие `HTTP_ADDR`, `STATIC_DIR`, `DATABASE_URL`, `REDIS_ADDR`, `REDIS_PASSWORD`, `MOCK_URL`, `MOCK_TOKEN`, `DEMO_MODE`, `LLM_MODE`, `GIGACHAT_*`. Новые env overrides длительностей/эксплуатационных лимитов документировать в таблице `.env.example` и README с единицами. Compose `environment` имеет собственный приоритет над env_file: не вводить туда повторные defaults для новых YAML-полей, которые помешают настройке файлом. Существующие обязательные container addresses и явно выбранные режимы сохранить.

Прямой запуск без файла сохраняет текущие Go defaults (gigachat, DemoMode=false); Compose по-прежнему может задавать demo/DEMO_MODE=true. Проверить разницу, а не унифицировать режимы молча. Default HTTP mock остаётся :8081, app — :8080.

### 3. Валидация и передача зависимостям

Проверять required-поля только выбранного процесса/режима; bool, duration, positive int; адрес слушателя с host/port (port 0 разрешён для изолированных тестов); корректность DSN и разрешённых схем URL без выдачи исходных значений. Для provider сохранить HTTPS и исключение HTTP только loopback в тестах, запрет credentials/query/fragment, проверку TLS и redirect policy. Чтение CA и создание клиента остаются обязанностью адаптера. Для mock URL сохранить HTTP между локальными контейнерами.

Все общие загрузки/валидация выполняются до NewStore/Ping/agent HTTP. В конструкторах допускается повторная локальная защитная валидация, но не повторное чтение env. Внедрить настройки таймаутов клиентов, HTTP server, health, chat, lifecycle, Redis session/rate limit, body limits через типизированные аргументы. Не менять значение существующих ограничений и не вводить новые соотношения таймаутов, которые запрещали бы текущие defaults.

Defaults получают только из env-default тегов через applyTagDefaults: вторых числовых/строковых defaults в Go нет. Отдельный MockHTTP сохраняет :8081/10s вместо app :8080/60s. После ReadEnv явно восстанавливать нулевые значения YAML, если соответствующий env не задан: cleanenv иначе повторно применяет defaults к пустой строке/false/0. Integer env принимаются в канонической десятичной записи без ведущего + и нулей, исключая неоднозначное основание 0 в cleanenv; диагностируется имя env.

SessionTTL — единый источник для Redis TTL и cookie MaxAge, вычисляемого в секундах. Для этой настройки требовать положительное целое число секунд; проверить нестандартное значение (например 30m → 1800 секунд в cookie) и удаление cookie при logout. Остальные длительности могут иметь дробные единицы согласно time.ParseDuration; окно quota передаётся в Redis PEXPIRE с округлением вверх до миллисекунды.

### 4. Константы по ответственности

| Категория | Размещение / правило |
|---|---|
| Статусы задач/заявок, общие идентификаторы ресурса и шагов | const-блок после импортов в `internal/core/types.go`, рядом с общими моделями; прежние JSON-значения |
| LLM modes, env names, default values, standard config paths | Именованные const-блоки в `internal/config`; исключить чтение env вне загрузчика, кроме явных тестовых переменных |
| Имена инструментов, роли, function finish reason, prompts и описания | const-блоки сразу после импортов в файлах использования agent.go/client.go/demo.go; одинаковые значения для schema/dispatch/trace |
| Cookie name, Redis prefixes, routes, headers, сообщения API/имитации | Const-блоки сразу после импортов в файлах использования, без отдельных constants.go/limits.go/prompts.go; совместно используемый межсервисный header — общее определение без циклов импортов |
| SQL DDL/queries/seed | Именованные SQL const-блоки после импортов непосредственно в store.go/server.go имитации; динамические значения передаются параметрами; статические статусы в SQL согласуются с доменными const |
| Фиксированные лимиты контракта/алгоритма | Локальные именованные const: пять инструментов, ограничения аргументов/выдачи, размеры ID, границы истории, OAuth reserve/retry, размеры ответа |
| Эксплуатационные значения | Поля config; значения по умолчанию — теги env-default в config.go; без повторных литералов в конструкторах |
| HTTP methods/status, TLS versions и стандартные значения библиотек | Использовать стандартные именованные константы, не создавать дубли `StatusOK = 200` |

Сохранить строковые JSON-поля и базовые типы core; переход на несовместимые enum-типы не требуется. Простые `0`, `1`, `nil`, `""` для проверки пустоты/счётчика, JSON-теги и структурные ключи не выносятся механически. Тексты тестовых данных остаются данными в seed/fixtures, но повторяющиеся ID и сообщения прикладной логики получают имена. Тесты сохраняют независимые литеральные ожидания внешнего контракта, чтобы ошибка значения общей константы не скрывалась одновременной подменой ожидания.

Избежать общего пакета `constants` для всех строк проекта: общие понятия в core, частные — у владельца. SQL после переноса не должен собираться из недоверенных значений; допустима композиция compile-time констант. Существующие JSON-поля, коды ответа, формулировки, seed и переходы не переписывать попутно.

### 5. Осмысленные имена Go-символов

Пользователь дополнительно потребовал понятные имена переменных и методов и исключение однобуквенных имён. Применить правило к собственному Go-коду в `cmd/`, `internal/`, новым config-пакетам и соответствующим тестам. Сторонние зависимости, сгенерированные файлы и frontend не затрагивать.

- Переменные, параметры и receiver-параметры описывают роль: `server`, `store`, `client`, `user`, `request`, `response`, `responseWriter`, `requestBody`, `onboardingPlan`, `accessRequest`, `operation`, `databasePool`, `decoder`, `err`.
- Однобуквенные объявления запрещены также в коротких областях: `i` → `taskIndex`/`messageIndex`, `e` → `err`, `r` → `request`, `w` → `responseWriter`, `t *testing.T` → `test *testing.T`, generic `T` → `Result` или более конкретное имя.
- Имена выбирать по смыслу, не глобальной заменой: `s` в разных местах означает Server, Store или Sessions; `r` может означать HTTP request или результат сервиса. Избегать бессодержательных `value`, `data`, `result`, если известна предметная роль.
- Многобуквенные общепринятые обозначения `ctx`, `err`, HTTP/JSON/SQL/URL/ID/TTL допустимы, если контекст однозначен; слова не удлинять механически. Не затенять импортированный пакет именем переменной, например `context` вместо `ctx`.
- Методы выражают действие и объект; имена должны отличать создание черновика, отправку, чтение и восстановление. Переименование не меняет бизнес-логику.

Ориентиры для переименования, окончательное имя проверить по всем вызовам:

| Текущее имя | Предлагаемое имя | Что уточняется |
|---|---|---|
| `Store.Plan` | `GetOnboardingPlan` | Получение плана адаптации |
| `Store.Complete` | `CompleteTask` | Завершение шага |
| `Store.Search` | `SearchKnowledge` | Поиск разрешённых инструкций |
| `Store.Resources` | `ListAccessResources` | Каталог запрашиваемых доступов |
| `Store.Draft` | `CreateAccessDraft` | Создание черновика |
| `Store.Confirm` | `ConfirmAndSubmitAccessDraft` | Подтверждение и инициирование отправки |
| `Store.Requests` | `ListAccessRequests` | Чтение своих заявок |
| `Store.Refresh` | `RefreshAccessRequestStatus` | Обновление результата сервиса |
| `Store.resolve` | `recoverOrCreateAccessRequest` | Чтение по ключу и условное создание |
| `Store.saveRemote` | `saveAccessServiceResult` | Сохранение ответа сервиса с защитой terminal |
| `Store.Messages` | `ListChatMessages` | Чтение истории |
| `Sessions.Allow` | `ConsumeChatQuota` | Проверка с расходованием квоты, а не чистое чтение |
| `id` | `generateIdentifier` | Генерация случайного идентификатора |

Синхронно переименовывать методы `core.Tools`/`Sessions`, реализации, demo/eval-подмены и вызовы; не оставлять старые внутренние aliases без причины. Строковые имена функций GigaChat (`get_onboarding_plan` и остальные), JSON/YAML/env-поля, SQL-колонки и HTTP-пути при этом сохраняются. Обязательные имена `main`, `ServeHTTP`, `Close`, `Error`, `Ping` и другие методы, действительно требуемые реализуемым внешним интерфейсом, сохраняются; наличие простого имени само по себе не повод нарушать контракт. Пустой идентификатор `_` допустим для действительно неиспользуемого значения, но не для сокрытия нужной обработки ошибки.

Проверка после реализации: адресно разобрать собственные Go-объявления (включая receiver, параметры, локальные объявления, циклы и type-параметры) через go/parser/go/ast либо эквивалентную точную проверку, а не только regex. Подтвердить отсутствие однобуквенных имён; компиляцией проверить полный перенос интерфейсов/вызовов; на ревью оценить смысл остальных имён. Спецификация поведения config не меняется: это внутреннее качество реализации.

### 6. Проверка после согласования реализации

Табличные config-тесты без сети: defaults, один YAML, env precedence включая false/empty, отсутствие optional файла, explicit missing, malformed/unknown/duplicate/multi-document/oversized YAML, неверные типы и сроки, required по процессам/режимам, отсутствие секрета в ошибках. Eval не должен требовать DB/Redis.

Регрессии: текущие Go unit/integration с изолированными схемами PostgreSQL и Redis; нативный протокол агента через локальный HTTP; статусы в SQL/JSON/инструментах; повтор/таймаут/поздний pending. Затем gofmt, go vet, go test, go build; project verify и проверка Compose/образа с файлами config без секретов. Live GigaChat для рефакторинга не нужен; новый платный прогон не включён. Контейнерный smoke проводить изолированно от работающего demo, без удаления его томов.

Текущий `npm run verify` сам запускает Compose-проект `onbo` с фиксированными портами, поэтому в этом изменении не использовать его обычный запуск рядом с работающим demo. Поднять отдельные PostgreSQL/Redis с уникальными именами, отдельными томами и динамическими loopback-портами, установить ONBO_TEST_DATABASE_URL/ONBO_TEST_REDIS_ADDR и вызвать `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1 -SkipIntegration`. Этот флаг пропускает только запуск штатного Compose: Go integration-тесты выполняются по явно заданным переменным. Smoke нового runtime-образа выполнить отдельными app/mock контейнерами в тестовой сети с отдельными именами и портами; рабочие app/mock и тома проекта onbo не перезапускать и не очищать.

Конфигурационные структуры/адаптация HTTP вынесены в config.go пакетов backend/agent/mock и cmd/onbo/cmd/mock. Структуры runtime и MustLoad находятся в internal/config/config.go. Требование размещения const проверяет scripts/check-go-style.go вместе с однобуквенными объявлениями.

## Risks / Trade-offs

- Более широкая область из-за переноса строк → перенос по пакетам с независимыми контрактными ожиданиями; не переписывать frontend/fixtures.
- Утечка DSN в ошибке стороннего парсера → безопасная оболочка ошибок и тест с контрольным секретом, без чтения рабочего `.env`.
- Невидимое перекрытие YAML окружением Compose → описать обе ступени приоритета, тестировать эквивалентный env-only и контейнерный путь.
- Изменение тестовых конструкторов → обновлять тесты вместе с внедрением типизированных настроек; покрытие нового loader включить в общий отчёт.
- Константа статуса в Go расходится с SQL/описанием модели → согласовать все места употребления и проверить внешний результат неизменными ожиданиями.
- Переименование задевает интерфейсы и многочисленные подмены → проводить согласованно по контракту, оставляя внешние строковые имена неизменными; проверять сборку и точную карту употреблений.

## Migration Plan

После одобрения плана: добавить loader/файлы и тесты, подключить точки входа, передать настройки модулям, перенести константы и согласованно переименовать внутренние Go-символы, обновить Docker/документацию и выполнить проверки. Старый env-only запуск сохраняется, рабочий `.env` не изменяется. Откат — возврат к предыдущей версии кода/образа; изменений схемы/данных нет. До одобрения изменяются только артефакты планирования.
